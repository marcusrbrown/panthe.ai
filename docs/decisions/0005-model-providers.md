# 0005: Model providers

## Status

Accepted (2026-09-27). Confirmed by the M0 inference-baseline and provider-matrix probes: a local baseline model profile, the hosted arm and fallback chain, and the offline-silence proof are all measured below. The shared heavy-work memory policy (coexistence probe) is **not** part of this ADR's Accepted gate and remains open — see Decision.

## Context

D02 requires full offline capability with optional hosted models; D22 requires a configured fallback sequence with no silent hosted fallback in offline mode; P06/P07 require guided local setup, role-based model assignment, and optional mixed local/hosted providers with measured fallback behavior.

## Decision

Local serving, confirmed: **Ollama 0.34.4** (native `/api/chat`, `options.num_ctx` for per-request context size, `format` for JSON-Schema-constrained output, tool calling). Baseline model profile, measured against 8 candidates × 2 context tiers × 40 prompts each ([tools/probes/inference-baseline/README.md](../../tools/probes/inference-baseline/README.md)): **`llama3.2:3b`, 4K context, `parallel=1`** — native schema validity 100%, kind-acceptable 83%, TTFT p50/p95 155/210 ms, completion p50/p95 706/1538 ms, server RSS 2783 MiB. `gemma4:e4b` is the quality runner-up (kind-acceptable 93% at 1K context, completion p95 3600 ms) but is not the default: population-scale cadence is latency-bound once a candidate clears roughly a 70% kind-acceptable bar, and gemma4:e4b's latency is several times higher for a smaller accuracy gain. `llama-server` (llama.cpp) is confirmed as a viable alternate server on the identical GGUF — close parity at 4K (83% kind-acceptable both servers; completion p95 1363 ms on llama-server vs 1538 ms on Ollama) — if Ollama's own concurrency or schema handling regresses. `parallel=2` on Ollama measured **worse** wall-clock throughput than `parallel=1` (1.05 vs 1.24 req/s) at roughly double the RSS (4728 vs 2780 MiB), confirming `parallel=1` rather than merely assuming it.

Reasoning-turn schedule and population allocation: at this baseline profile's measured p95 (1538 ms), a single bounded queue (concurrency 1) supports **~39.0 reasoning turns/minute** system-wide. Spread flat round-robin across 27 characters (7 gods + 20 inhabitants), that cadence is already below the 30 s per-character acceptance-plan starvation threshold — a flat round-robin is not viable at full population, confirming the concern `open-decisions.md` flagged for the M0/M2 probes. The scheduling policy this ADR settles for M2+ is **gods-first, inhabitants-on-routines**: the 7 named gods hold priority access to live reasoning turns (their cadence must clear the 30 s p95 acceptance target); the 20 ordinary inhabitants run primarily on routine/heuristic behavior (the same pattern defaults.md already uses for absent-player mortals, and the background-scheduling capability W06 already requires) with reasoning turns granted from whatever queue budget remains, not on a flat per-character round-robin. This tunes cadence under D23 delegated authority; it does not reduce the seven-god content roster or remove inhabitant participation — defaults.md explicitly forbids hiding an inference bottleneck by cutting content, and this policy is the alternative to that.

Hosted, confirmed: the arm is **OpenCode Go** ([tools/probes/provider-matrix/README.md](../../tools/probes/provider-matrix/README.md)). Its free models (`space-bunny-free`, `longcat-2.5-preview-free`) are reachable over `/chat/completions` with the `opencode-go` credential, both producing valid structured actions (via the repair pass, see caveat below) and supporting tool calls this run — measured latency p50 ~5.0 s and ~19 s respectively (longcat markedly slower). The confirmed order is Go's free models first, then its paid model (`mimo-v2.5`) as the in-Go fallback. **OpenCode Zen is a scope note, not a usable arm for M0**: its `zen/v1` free tier returned a typed 403 `FreeTierError` on every tested request (2/2 this run; 23/23 in a dedicated prior sweep across headers/endpoint/key-source combinations, plus a targeted follow-up for a reported request-shape heuristic that also didn't reproduce it) from what the error itself identifies as a non-public inference service. Zen and Go share the identical underlying credential (`opencode`/`opencode-go` auth.json entries hold the same key, confirmed by direct comparison) — this is a deliberate provider-side scope gate, not a missing key or a subscription-tier difference. Configured fallback sequence, confirmed working: Go free → Go paid → local Ollama → routine-only. OpenAI/Anthropic remain contract-tested only (no keys, per plan scope): the shared `repair.ts` pass produces an identical parsed action across both adapters' fixture shapes, and a no-valid-action fixture fails identically across both.

Offline proof, confirmed silent on the wire: 20 offline-mode requests produced zero hosted-client constructions in this probe's own fallback router, and a `sudo`-elevated packet capture (all interfaces, including loopback/IPv6/utun/awdl, plus a DNS-query log) observed **zero packets** matching a resolved provider IP or a provider-host DNS lookup. A positive control — one real, non-offline request routed through the identical capture path — measured 39 provider packets, confirming the capture path can see provider traffic and that the offline silence is real, not a blind capture.

Provider abstraction, confirmed with a caveat: Vercel AI SDK 7 (`ai@7.0.93`) with `@ai-sdk/openai-compatible` for Ollama/llama.cpp/OpenCode Go, and `@ai-sdk/openai`/an Anthropic adapter for their native APIs, parameterized by base URL so every server shares one path — this shape held up. The caveat: **no tested Go model produced natively schema-valid output** — every tested response (`space-bunny-free`, `longcat-2.5-preview-free`, `mimo-v2.5`) needed the shared repair pass (`repair.ts`: extract JSON, re-validate) to reach a valid parsed action (native validity 0% across all three, repaired to a valid action in every case that didn't outright fail). The repair path is therefore not an optional resilience feature for hosted models — it is the load-bearing mechanism for every tested Go model; any future hosted provider addition must budget for it rather than assume native JSON-Schema compliance.

**Heavy-work memory policy — superseded by re-measurement, kept for history**: on the 16 GB baseline, an earlier pass read the M0 coexistence probe as settling an **admission-controlled queue** — a new image job starts only when free+inactive memory is ≥ 3 GiB, and only one image job runs at a time — measured against a renderer+LLM-only baseline (LLM p50/p95 611/1535 ms) at LLM p95 **-10.6%** (1373 ms) while completing 7/7 queued image jobs; a global mutex (+1404% LLM p95, 23094 ms) and unconstrained concurrency (+44%, 2216 ms) were both measured worse and rejected; a stricter 5 GiB admission gate starved image generation entirely (0/7 images completed). A follow-up review found the original per-scenario latency sampling mixed successful and failed/timed-out requests with no evaluability floor, so the -10.6% admission-queue figure above is **not trustworthy** and this call does not stand.

**Heavy-work memory policy: NOT decided.** A corrected re-measurement (success-only latencies, an evaluability floor of ≥20 successes and ≤5% error rate) is only directly comparable for the one pair of candidates measured together in the same session: baseline (A) LLM p50/p95 645/1242 ms (60/60 successes) and the 3 GiB admission queue (D@3GiB) LLM p50/p95 1574/3086 ms (60/60 successes, 6 images completed) — a **+148% p95 penalty**, the opposite of the superseded claim above. Unconstrained (B: 1315/2216 ms p50/p95, 7 images completed), the single global mutex (C: 22784/23094 ms, 8 images completed), and the 5 GiB admission gate (D@5GiB: 626/960 ms, 0 images completed) are **first-round, not evaluable — no comparable baseline**: they were measured in a different session than the re-measured baseline, without success/attempt counts recoverable for the evaluability floor, so no percentage change or accept/reject verdict can be assigned to them this round. **Verdict: inconclusive — no candidate policy is supported by the current evidence**; A and D@3GiB are the only evaluable pair, and even that pair rejects the 3 GiB threshold. M1 must re-measure B, C, and D@5GiB together with a corrected baseline before any of them can be closed (accepted or rejected), plus test an admission threshold between 3–5 GiB, rate-limited/backpressured generation instead of a hard admission gate, and scheduling image jobs into LLM idle windows rather than gating on memory alone. LLM inference must never be blocked by an image job regardless of which policy M1 settles on — that constraint holds independent of the open threshold question. See [tools/probes/coexistence/README.md](../../tools/probes/coexistence/README.md) for the full re-measurement; this is the canonical wording, also referenced from [ADR-0003](0003-simulation-service.md) and [ADR-0007](0007-local-image-generation.md).

## Consequences

**Superseded by measurement (kept for history)**: model quality/latency tradeoffs were probe outputs, not fixed at proposal time — they are fixed now, see Decision above. The AI SDK structured-output concern was real but only partially: native structured output was never observed from a tested Go model, so provider adapters do rely on a hand-rolled repair pass rather than the SDK's native parsing alone — but that repair pass is a designed, shared, tested component (`repair.ts`), not an emergency fallback. Serializing LLM and image work was assumed to bound peak memory at some throughput cost; a global mutex was measured to cap effective throughput far more severely than assumed (+1404% LLM p95, not a mild slowdown) and stays rejected, but the admission-controlled queue's own -10.6% figure did **not** hold up under re-measurement (+148% instead, see Decision) — the memory-sharing policy is open, not settled, and the M4 Pro profile question is downstream of that unresolved threshold.

At 27 characters (7 gods + 20 inhabitants), the measured ~39 turns/minute schedule already exceeds the 30 s starvation threshold under a flat round-robin — addressed by the gods-first/inhabitants-on-routines allocation in Decision above, not by reducing the roster.
