# A proposal acknowledged before it was durable was lost on a crash, and its retry answer did not survive a restore

## Problem

`/proposals` is how fixtures and operators feed the world. It answered 202 as soon as the proposal was in an in-memory queue. A crash before the next tick lost an input the caller had been told was accepted, with no outcome and no trace. The first durable version stored who was consumed but kept the outcome in the trace tables, and archives copy the journal and not the trace, so a retry on a restored branch failed.

## Symptoms

- SIGKILL after a 202 and before a tick: after restart the proposal never ran. Nothing in the store said it had existed.
- The queue drained into a tick by arrival timing, so the tick an input ran in was not persisted input to the world.
- Export, import, then retry of a consumed `proposalId`: the handler found the journal row consumed, looked for its trace outcome, found none, and returned a 500 ("consumed at tick N but has no recorded outcome").

## What Didn't Work

1. **The in-memory queue.** The handler appended and acknowledged; a failed tick put the drained entries back with `requeue`, which handled a commit failure and not a crash:

   ```ts
   // apps/simulation/src/server.ts, handleProposal (before)
   externalQueue.enqueue({
     id: createProposalId(),
     proposal: intake.proposal,
     observation: observationResult.value,
   });
   return jsonResponse({ ok: true, queued: true }, 202);
   ```

   The proposal id was also generated by the service, so a caller that lost the response could not retry safely.
2. **A journal that recorded only "consumed".** The table had `consumed_tick` and nothing else, and a retry read the outcome from the trace:

   ```ts
   // journalStatus (first journal version)
   const outcome = getProposalOutcomeByProposalId(traceDb, entry.proposalId);
   if (!outcome) {
     return jsonResponse({ ok: false, error: `proposal ${entry.proposalId} was consumed at tick ${entry.consumedTick} but has no recorded outcome` }, 500);
   }
   ```

   The archive copies `external_proposals` and does not copy trace records ([ADR-0008](../../decisions/0008-world-state-and-client-transport.md#import-and-restore)). On a restored branch the row said consumed and the outcome was gone.

## Solution

**Journal before the 202.** Intake writes the entry in one `IMMEDIATE` transaction and only then answers. The entry targets the tick after the persisted clock, and the producer supplies the id.

```ts
// packages/persistence/src/journal.ts:141-167 (abridged)
const existing = getExternalProposal(db, input.proposalId);
if (existing) {
  return { kind: sameContent(existing, input) ? "existing" : "conflict", entry: existing };
}
const { tick } = db.query("SELECT tick FROM clock WHERE id = 1").get();
// next input_order = MAX(input_order) + 1
db.run(`INSERT INTO external_proposals (input_order, proposal_id, target_tick, proposal, observation)
        VALUES (?, ?, ?, ?, ?)`, [next, input.proposalId, tick + 1, /* json */]);
```

- A journal failure is a 500, never a queued success (`apps/simulation/src/server.ts:638-667`).
- A retry with the same content returns the entry's status: 202 while pending, the terminal status once consumed. The same id with changed content is a 409 (`server.ts:568-590`, `:668-676`). An id the trace already holds for a routine's proposal is also a 409 (`server.ts:642-653`).

**Consume inside the tick's commit transaction.** `traceWorldTick` runs in `commitTick`'s `onCommitted` hook, so marking the entry consumed commits or rolls back with the tick (`apps/simulation/src/tick.ts:300-303`, `:379-393`; `packages/persistence/src/journal.ts:209-230`). A rollback leaves the entry pending, and the next tick runs it once. This is the pattern in [A write that must share a tick's fate runs inside its commit transaction](../best-practices/side-effects-inside-the-commit-transaction-2026-09-28.md).

**Keep the outcome on the journal row.** The row is either pending or consumed with its terminal outcome, and a rejection always names its reason:

```sql
-- packages/persistence/src/store.ts:71-86
consumed_tick INTEGER,
outcome TEXT CHECK (outcome IN ('committed', 'rejected')),
reason TEXT,
CHECK ((consumed_tick IS NULL) = (outcome IS NULL)),
CHECK ((outcome IS 'rejected') = (reason IS NOT NULL))
```

A retry reads its status from the row (`server.ts:569-590`), so it resolves the same way on a restored branch as on the original. Import validates the same pairing and rejects an outcome without consumption, a reason on a committed row, and a reason that is not a known rejection code (`packages/persistence/src/archive.ts:845-863`). The "consumed with no outcome" state cannot be stored, so the 500 path is gone.

## Why This Works

A caller that receives a 202 has been promised the proposal will run, and the only promise a process can keep across a crash is one the store already holds. Writing the entry before answering makes acceptance and durability the same event. Consuming it in the tick's transaction makes "ran" and "marked consumed" the same event, so no crash window has a proposal that ran twice or ran zero times. The retry answer has a second requirement: it must be readable from whatever a restore copies. The trace is not copied, so the outcome moved to the row that is.

## Prevention

- Never acknowledge before the durable write. If the write can fail, the failure is the response.
- Anything that answers a retry must travel with whatever restore, export, or replay copies. Check the answer's source against the archive's contents.
- Make impossible states unstorable: two `CHECK`s replaced a runtime "consumed without an outcome" error.
- Tests for each half:
  - `apps/simulation/src/proposal-journal.test.ts:264` — accept, close, reopen: it runs exactly once.
  - `apps/simulation/src/proposal-journal.test.ts:379` — a tick that fails to commit leaves the entry pending with no outcome.
  - `apps/simulation/src/proposal-journal.test.ts:410` — retry returns the status, and changed content is a 409.
  - `apps/simulation/src/proposal-journal.test.ts:602` — export, import, reopen from the slot file alone, then retry a committed and a stale-rejected proposal.
  - `packages/persistence/src/journal.test.ts:215` and `:242` — outcome stored on the row; rollback leaves it pending.
  - `packages/persistence/src/archive.test.ts:1231` — each invalid pending/consumed combination is rejected on import.
- The compiled-sidecar scenario SIGKILLs right after a 202 and checks the proposal runs once on the catch-up tick ([m1-living-world](../../../tools/scenarios/m1-living-world/README.md), S12), with a positive control that deletes the journal entry and must fail.
